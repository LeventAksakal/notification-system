# The server's endpoint code owns the HTTP contract; the spec and clients are generated from it (0024)

## Question
Who owns the OpenAPI document: the HTTP server that implements it, or the client apps that call it? Put as a build question: is `api/openapi.yaml` written by hand and the server generated from it, or is the server written and the document generated from the server?

## Rule
Change the API in `internal/httpapi` (operations registered from `api.go` and the per-operation files beside it, request and response types in `contract.go`, the WebSocket message in `stream_event.go`, limits from `internal/notification/limits.go`), then run `task gen`: it writes `api/openapi.yaml` and the typed Go client in `test/apiclient`. Never hand-edit either.

## Context
Owner, 15 Nov 2026, reviewing record 0004: "who owns the open api spec? an http server implementing it or client apps calling it?" The producer owns a contract: the server's code is what runs, so the document has to come from it, and every consumer (a web or mobile app, another service, our acceptance tests) generates its client from the committed document. Record 0004 had chosen the reverse (a hand-written spec, server stubs generated by oapi-codegen) and compared it only with comment annotations (swaggo), not with a library that derives the document from the handler types. A hand-written spec is the source only when several server implementations share one contract, which this project does not have.

How it runs: one binary. At start-up `internal/httpapi` registers 15 Huma operations on a `net/http` ServeMux (humago adapter); Huma builds the OpenAPI 3.1 model from their Go types, validates each request against it before the handler runs, and the server serves it, downgraded to 3.0.3, at `/openapi.json`. `/v1/ws` is a plain `net/http` handler outside Huma; it is added to the same document by hand, with its message type (`StatusEvent`) taken from `stream_event.go`; its full contract is the AsyncAPI document of 0027. `go generate` writes the same 3.0.3 document to `api/openapi.yaml`, then oapi-codegen turns it into `test/apiclient`.

## Options
1. Spec-first with oapi-codegen (record 0004, now superseded). The YAML is the source; a strict server interface is generated, and kin-openapi validates requests against the YAML. The document can never lag the server, but it is a second language to write (about 700 lines of YAML beside the Go), every limit is written twice and tied together by a test, and the server's real behaviour (headers it sets, errors it returns) still has to be described by hand.
2. Code-first with Huma v2 (chosen). Operations and their types are Go; tags carry formats, enums and limits, and limits are read from the `notification` constants, so they are written once. Validation and the document come from the same types, so they agree, except where Huma's validator is looser than the schema it publishes: it ignores an optional property set to null, reads the first of a repeated parameter and treats an empty one as absent. `refuseNull` (`api.go`) and `singleValues` (`param_parsing.go`) refuse those, as the old server did. Costs: Huma's validation messages and its error model are not ours, so `errors.go` maps them onto the existing `Error` body (400 `invalid_request` with `details[].field`, 413, 422 for a reused key, 503 with `Retry-After`); a few Huma defaults are changed to keep the published document compatible (no `$schema` links, no default error response, plain integers, open response objects). Huma inlines parameters and response headers instead of `$ref`-ing `components.parameters` and `components.headers`: the wire is the same, but a generated client loses the named parameter types (`IdempotencyKey`, `CorrelationId`, `Limit`, `Cursor`), and the list of templates gets a named schema (`TemplateList`).
3. Code-first with swaggo comments. The document comes from `// @Param` comments above the handlers, which the compiler never checks: the comment and the code drift, and request validation still needs a separate library.

## Decision
Option 2. Option 1 makes the client side own a document the server must then obey; option 3 generates the document from text the compiler cannot check. With Huma, the types the handler reads are the document, so a change that would break clients shows up in the generated diff and in the breaking-change check before it merges.

The move kept the published contract: `oasdiff breaking` against the 1.3.0 document reports no change (with `--flatten-params`, since a path-level parameter now sits on each operation), so the version stays 1.3.0. Clients regenerate from `api/openapi.yaml`; this repository's own client is `test/apiclient` (oapi-codegen, chosen because it emits plain `net/http` code with typed responses per status and needs no runtime beyond `oapi-codegen/runtime`).

`/docs` still serves the vendored Scalar bundle: Huma's built-in docs page loads Scalar from unpkg.com, and `/docs` calls no other host.

## Confirmation
- `TestCommittedSpecIsGenerated` (`internal/httpapi`) and the CI step "Generated code is up to date" fail when `api/openapi.yaml` or `test/apiclient` differs from what `go generate` writes.
- The CI step "API contract keeps every client working" runs `oasdiff breaking --fail-on ERR` against the base revision's spec (`task api:breaking` locally).
- `.claude/agent-policy.json` marks `api/openapi.yaml` and `*.gen.go` as generated and `internal/httpapi/{api,contract}.go` as contracts; `tools/ownercheck` fails a lane whose diff regenerates the spec, which also catches an operation changed in any other file of the package (`reschedule.go`, `template_versioning.go`, `stream_event.go`), since the spec is generated from them all.
- `TestR10LimitsAgreeSpecAndCore` (`test/acceptance`) reads the limits from the generated document and compares them with `internal/notification/limits.go`.
