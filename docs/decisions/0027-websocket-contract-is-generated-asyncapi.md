# The WebSocket contract is an AsyncAPI document generated from the server's types (0027)

## Question
OpenAPI describes the HTTP API. What describes `/v1/ws`, the live status stream, so that a client author can build against it without reading the server's code?

## Rule
`api/asyncapi.yaml` is generated by `task gen` from the server's Go types (`httpapi.AsyncAPIYAML`). Its payload schemas are copied from the same Huma registry that produces `api/openapi.yaml`, and it is served at `GET /asyncapi.yaml`. Nobody edits it by hand.

## Context
The owner, 16 Nov 2026: "that's what OpenAPI is for HTTP but for ws. it isn't there so we can't see the ws contract". Record 0022 had weighed AsyncAPI and left it out: one server-to-client message would only repeat the route already in the OpenAPI document. Since then the stream has gained a snapshot and an ordered status message (`seq`, decision 0013), a 503 refusal while live updates are unavailable, and close codes a client must handle. The owner's standing rule applies: the producer owns the contract, so it is generated from the server's code, as the HTTP spec is (0024).

## Options
1. **A small builder over the Huma registry** (chosen). It needs no new dependency, and the HTTP and WebSocket contracts share one schema source; a test asserts the payload schemas equal the OpenAPI components. Trade-off: it covers only the part of AsyncAPI 3.0 we use. The HTTP refusals and close codes live in `x-handshake-refusals` and `x-close-codes` extensions, because AsyncAPI has no object for either.
2. **`github.com/swaggest/go-asyncapi`'s 3.0 reflector.** A maintained library, but it derives schemas with `swaggest/jsonschema-go`, a second schema source with its own tags and naming, so the two contracts could drift.
3. **A hand-written `asyncapi.yaml`.** No code at all, but the consumer-owned style the owner rejected for HTTP in 0004.

## Decision
Option 1. The document covers the channel and its two query parameters (`notificationId`, `batchId`), the `snapshot` and `statusChange` messages with examples built from real `StatusEvent` values, the handshake refusals in the order the server checks them, and every close code the server or its WebSocket library sends. Clients send nothing; a data message is closed with 1008. Every `StatusEvent` field now has a description, which the OpenAPI document gains as well. This supersedes the AsyncAPI sentence in 0022.

## Confirmation
- `go generate ./...` followed by `git diff --exit-code` in CI's static job fails on a stale `api/asyncapi.yaml`.
- `TestCommittedAsyncAPIDocumentIsGenerated` checks the committed file.
- The tests in `internal/httpapi/stream_asyncapi_test.go` check the payloads against the Go type and against the OpenAPI schemas, the close codes against the server's constants, the query parameters, the 503 refusal and the route serving the document.

## Numbers
| Number | Value | Where it comes from |
|---|---|---|
| Close code, subscriber too slow | 1008 (policy violation) | RFC 6455 §7.4.1; the server closes a subscriber whose send buffer is full |
| Close code, live updates went down | 1012 (service restart) | IANA WebSocket close-code registry; the client should reconnect later |
| Close code, server shutting down | 1001 (going away) | RFC 6455 §7.4.1 |
| Close code, protocol error | 1002 | RFC 6455 §7.4.1, sent by the WebSocket library |
| Abnormal closure seen by the client | 1006 | RFC 6455 §7.4.1; never sent on the wire, reported locally when the connection drops |
| Ping interval and write timeout | 20 s, 10 s | The server's existing constants beside the WebSocket handler, which state their own reasons; the document reads them, it does not set them |
